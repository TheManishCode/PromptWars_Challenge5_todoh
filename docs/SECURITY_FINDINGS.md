# Security findings register (red-team pass, thread C)

Started 2026-11-01 on branch `feature/wall-and-pentest` (base 95aa06c). **This is evidence from specific probes, not a certificate.** Passing these tests does not prove the system
is secure. Every row says what was run, what it showed, what changed, and what is still open. Exploits are kept as regression tests under `tests/pentest/`; throw-away probes
(timing, live sockets, parser fuzzing) are in `_audit/pentest/` outside the repository.

Severity is for the product as it is used today (one person, loopback). "Hosted" notes say what changes if it is exposed (see Phase 2 and 5 of the v6 prompt: no shared mode exists yet).

## Recommendations not built (each needs a decision or a larger change)

- **Authenticate replies.** A vendor reply is matched by `In-Reply-To` (needs the thread) or by the sender address alone (a spoofable `From`), so anyone can forge a quote or a "stop" for a vendor. Parsing the receiving server's `Authentication-Results` (`dkim=pass`/`spf=pass`/`dmarc=pass`) and labelling a reply "sender not verified" would narrow this, but many small vendors fail DKIM, so it changes what the user sees: an owner decision. Quotes already need the user's confirmation, which is the real control.
- **One global lock.** `web/app.py` serialises 93 route bodies behind one `RLock`. Measured: planning takes about 0.12 s, so one user never notices; a shared deployment would serialise every visitor, so per-plan or per-workspace locks belong with Phase 2.
- **Kill the voice engine on timeout.** F-006 is bounded, not eliminated; a subprocess per transcription would let a runaway decode be killed.
- **A default API token on loopback.** Today any local process can call the API; generating a per-start token needs the frontend to read it.

## Known gaps handed to other lanes (not mine to fix)

- **Thread A (Phase 1/2/3):** plan versions have no parent-hash chain and no signature by default, so deleting the newest version file silently rolls a plan back (`plan_store.py`; also v6 1.4). In a shared deployment every store except plans is global, so one visitor's venue-access record, quote or contact would affect all. A web request can resume the kill switch (`POST /api/autoreply/resume`) with only the process-wide CSRF value; fine for one local owner, not for shared mode.
- **Thread B (Phase 4/5):** F-001. The per-IP limiter dictionary (`writes` in `web/app.py`) never forgets an address (slow memory growth); the limiter trusts `request.remote_addr`, so behind a proxy all visitors share one budget until the trusted-proxy setting exists.
- **Owner:** the API has no token by default on loopback, so any local process or browser extension can use it; a vendor-forged "stop" or reply from an address that can read the thread headers is documented as unauthenticated; real-mailbox behaviour and real-model injection resistance have never been run.

## Not tested (no claim made)

Anything against a real browser, a real mail server, a real WhatsApp gateway, a real model, a real proxy or a real host; shared mode (does not exist yet); the frontend (`web/static/*`, not edited); timing side channels beyond use of constant-time comparison; denial of service by sustained high volume (only the specific cases above); the optional real voice engine.


# Round 3: the integrated branch, before it goes anywhere (2026-11-01, after frontend v20)

Scope: everything on `integration/frontend-v20` (workspaces, import/export, backups, limits, hosting checks, the wall, the room's own JavaScript). Method: read the new code,
then attack it; each row below has a test that **failed before the fix** (checked by stashing the fix). Same limits as above: this shows these attacks and what happened, not that
nothing else works.

| ID | Severity | Where | Attack | Fix |
|---|---|---|---|---|
| F-010 | **High** (anyone who can hand someone an archive) | `transfer.py` import | The archive model only demands `validation.passed`, so a plan whose vendors, prices and checks were typed by hand, with every hash re-sealed, was imported and shown as VERIFIED | every version is run through this application's own validator (against its parent) before anything is written; one that does not pass here is refused, naming the plan. Honest exports round-trip (the whole `test_transfer.py` still passes). **Limit:** the symbolic (PDDL) status inside a plan is not recomputed (it needs the solver) |
| F-011 | Medium | `transfer.py` | A failure on a plan's second version left its first version in the store (versions were only counted as created after all were saved) | the plan is registered for undo before its first save |
| F-012 | Medium | `transfer.py` | The id remap was a text replace of the old id over the whole plan JSON: an archive whose plan id is one character (`a`) rewrote every `a` in every key and word, corrupting or crashing the import | the `plan_id` field is set; no text is replaced |
| F-013 | Medium | import route / `workspaces.py` | The storage quota was checked before the archive was read, so one request could add up to 60 MB past it | the unpacked size is offered to the quota before anything is written (`check_write(incoming=)`); 507 `workspace_quota` |
| F-014 | **High** (cross-tenant disclosure) | `arcade_pulse.py` | One pulse object for the whole process: `GET /api/arcade/pulse` showed every visitor the first 100 characters of the last request any visitor typed, plus the last error text and run timings | each workspace has its own pulse; hooks reach it through a context variable bound per request |
| F-015 | Medium | `web/limits.py`, `app.py` | Per-address limits counted each IPv6 address separately; one customer owns a /64 (2**64 addresses), so workspace-creation and write limits gave an IPv6 attacker no limit | IPv6 callers are counted as their /64 |
| F-016 | Medium (data integrity under load) | `workspaces.py` | The least-recently-used eviction could drop a workspace a request was still using; the next request built a second `Workspace` with a second lock for the same directory, so two requests changed the same files unsynchronised (and in-memory assistant proposals and voice sessions vanished) | a workspace with a request in flight is never evicted |
| F-017 | **Medium-High** (backups) | `backup.py` | Per-workspace databases (`jobs.db`, WAL mode) were copied with a raw file copy, plus their `-wal` and `-shm` side files copied separately at other moments: a backup taken while the server runs could mix two moments and be torn | every `.db` is copied with SQLite's online backup; side files are never copied alone. Test: committed rows that exist only in the write-ahead log are in the restored copy |
| F-018 | Medium | `backup.py` | (a) `verify_backup` read and hashed any file a manifest named, including `../` paths outside the backup; (b) a symlink inside a backup was followed by restore and its target copied in | a manifest path that leaves the backup, and any link inside it, fail verification |
| F-019 | Medium (operations) | `web/__main__.py` | Nothing stopped a second server process on the same data directory, although every lock, limit and live-workspace set is per process | the shared-mode server takes an exclusive lock on `<data dir>/.server.lock` and refuses to start if another holds it |
| F-020 | Medium | `wall/routes.py`, `app.py` | The wall counted callers by `remote_addr`: behind the required proxy every visitor shared one budget, and a forged header was not the problem but the proxy's address was | the wall uses the app's own caller address (trusted-proxy header, IPv6 as /64); its cookie is always `Secure` in shared mode |
| F-021 | Medium (only behind a proxy that disagrees with waitress) | waitress | A request with both `Content-Length` and `Transfer-Encoding: chunked` is read as chunked and the bytes after it as a second request | **tested, not changed**: nginx 1.30.6 in front refuses all four smuggling shapes (one answer each, 400 or 501); documented in `HOSTING.md`; any other proxy is untested |

Also fixed (no separate id): the arcade page now checks that a saved lead's link is `http(s)` before making it a link (the server already refuses anything else); SIGN no longer throws on plain HTTP (`crypto.randomUUID` is secure-context only); in shared mode a write refused because the workspace cookie was lost now tells the person their session was lost instead of printing "not found"; one unclosed database connection in `workspaces_admin`.

**Checked and held (round 3):** a 40-second soak of the real waitress server with 12 concurrent visitors doing plans, ledger, guest import, export, import, plan and workspace deletes under constant eviction (`max_live=6`): no 5xx, no server error log, flat file descriptors and threads; 1,500 requests across every route in shared mode with mutated bodies: no 5xx, no server path, no other workspace's text in any answer; 300 workspaces with eviction churn: memory, descriptors and threads flat; the frontend: no `innerHTML`, `eval`, `document.write`, `postMessage` or inline script anywhere in the room's JavaScript, and the CSP forbids them anyway; 17 HTTP request shapes against waitress directly (bad Host headers, duplicate Host, oversize headers/URL, negative or huge `Content-Length`, double and obfuscated `Transfer-Encoding`, traversal in `/static`): all refused or harmless; repository history, all branches: no key, token or private-key pattern.

**Known gaps (not fixed):** an import is not atomic across stores if the process is killed mid-way (a plan can exist without its ledger); the symbolic status of an imported plan is trusted (F-010 limit); pending assistant proposals live in memory (thread A's SQLite queue is not in this branch); the room has no screen for the do-not-contact review, bounce acknowledgement, the owner digest, explore/deals or approved answers; `blob:` and `wasm-unsafe-eval` stay in the CSP until the real models have been run without them; anonymous workspace creation can still be exhausted by many addresses (a global cap of 60 an hour is the protection and the cost); the real models, a real browser on a phone and a real proxy other than nginx were not tested.
