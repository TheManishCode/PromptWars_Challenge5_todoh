# Production readiness review

A review of this system against the usual production design principles, written after building the workspace, limits, observability and backup work and after two red-team passes (`docs/REDTEAM.md`). It says what is in place, what is partly there and what is missing, and it does not call the system production ready: **it is ready for a small, owner-operated hosted trial behind a reverse proxy, not for open internet scale.** Nothing here was run on a real host, behind a real proxy, under real load or in a real browser.

## Shape of the system (what the design assumes)
One Python process (Flask, threads) on one machine, state in files: immutable hashed JSON plan versions, append-only JSONL logs, SQLite for jobs, the workspace directory and the wall. A workspace is a directory with its own application objects; isolation is structural (`docs/WORKSPACES.md`). The deterministic core (parser, planner, validator, scheduler) holds the guarantees; language models only propose or phrase and have no authority (`docs/MODEL_INPUTS.md`, `tests/test_llm_boundary.py`). This is a sound shape for tens to a few hundred light users on one box. It is not horizontally scalable (file locks, in-memory sessions and caches, one process per data directory), and nothing below pretends otherwise.

## Principle by principle
| Principle | State | Evidence and what is left |
|---|---|---|
| **Fail closed, validate at the boundary** | Strong | Strict models (`extra="forbid"`) on every request body; start-up refuses unsafe shared configurations by name (`hosting.shared_mode_problems`); hostile archives refused before any write; unknown state refuses. Left: schema upgraders for stored data (v6 1.2, not built). |
| **Least privilege, defence in depth** | Strong for what exists | Model has no authority; mutating tools only file proposals a human approves; guest workspaces have no sending channel *and* the sending routes refuse (two layers); owner routes need a separate token; CSRF per workspace; host and origin checks. Left: no helper/view-only credential, no global owner send gate (so guest sending cannot be enabled). |
| **Isolation of tenants** | Strong | Per-workspace stores; a route sweep generated from the route table checks 58 plan-scoped routes and fails if isolation is broken (it did, on purpose, for 33 routes). Left: tenants share one process, one disk and one set of model/search quotas (per-workspace caps limit, not partition, them); a memory or CPU bug in one request can affect all. |
| **Secrets and configuration** | Good | Environment only (a `.env` file is refused in shared mode); redaction of secrets from logged errors; prompts hold no secrets (tested); `requirements.lock` is hash-pinned; gitleaks over history is clean apart from fake test keys. Left: no secret rotation procedure beyond restarting with new values; the workspace secret derives CSRF values only, so rotating it only logs people's pages out of writes until they reload. |
| **Rate limiting and resource bounds** | Good | Per address and per workspace write limits (bounded memory), model calls and tokens per workspace, a fair share of slow searches, storage and plans-a-day quotas, lookup caps, idle timeout and connection cap, upload caps with a measured envelope, archive limits. Left: a patient attacker can pin the workspace slots (R-10); read routes are not rate limited; planning has no global concurrency cap beyond the per-address write limit; a trickle client inside the idle timeout is only stopped by a proxy. |
| **Observability** | Basic but real | Request id on every answer and error; structured access log with no sensitive fields (tested); counters by status class and latency band; `/healthz` and `/readyz`; per-workspace decision logs. Left: no metrics export (Prometheus or similar), no tracing, no alerting, no log shipping or rotation of the process log (the supervisor's job), no latency percentiles. |
| **Graceful degradation** | Good | No model: documented no-model answers. Model budget spent: degraded answer. Disk full: 507 with a code. Outside service down: a named error, never a silent switch to another source. Poison email: becomes a "could not be read" notice. Left: the transcriber thread cannot be killed on timeout (R-gap); no circuit breaker around outside services beyond their own timeouts. |
| **Data durability and recovery** | Partial | Plan versions are create-only and read-only; backups with a verified manifest while running; restore into an empty directory re-applies deletions (tested, including a workspace and a plan deleted after the backup). Left: no automatic or scheduled backup; backups are plaintext; **no parent-hash chain on plan versions** (deleting the newest file silently rolls a plan back: v6 1.4); no JSONL `verify`/`repair` (a corrupt line blocks a store: v6 1.3); pending assistant proposals and voice sessions are memory-only and lost on restart (v6 1.1); no point-in-time recovery; no cross-store consistency check. These are the durability phase, which this work did not do. |
| **Privacy and deletion** | Good | One page says what is stored and for how long (`docs/PRIVACY.md`); deleting a plan removes its files and its lines from the logs and writes a minimal tombstone; deleting a workspace overwrites and removes everything; export and import under hostile-input rules. Left: backups and exports are plaintext copies the application cannot reach; no encryption at rest (host disk encryption is unverified); retention of non-empty idle workspaces is an owner decision. |
| **Change safety (releases, migrations, rollback)** | Weak | Tests run on every change (about 2,700 here, including the browser tests) and CI is configured with pinned actions and a locked install, but CI has never run on GitHub; no staged rollout, no migration framework (v6 1.2), no feature flags beyond environment settings. Rolling back code is safe for data (plan files are immutable) as long as no schema change has shipped. |
| **Supply chain** | Good | Hash-pinned lock file; `pip-audit` clean on the day it ran and report-only in CI; vendored front-end files have a manifest and a test; nothing downloads code at run time. Left: `pip-audit` is not blocking; no SBOM; the optional `faster-whisper` engine and its model are the owner's to vet. |
| **Operability** | Basic | Start-up checks, signal-driven drain, `docs/RUNBOOK.md`, admin commands for workspaces and backups. Left: no zero-downtime upgrade, no high availability, no automated alerting, no capacity test. |
| **Honesty of claims** | Strong | Test counts are measured and dated; every ADR has "honest limits"; behaviours not run on a real model, mailbox, browser or host are said to be unrun. |

## Residual risks, most serious first
1. **No identity recovery.** Clearing the browser loses a workspace unless the person exported. An owner decision (`docs/WORKSPACES.md`).
2. **Durability gaps** (v6 phase 1, unbuilt in this work): plan rollback by deleting a file, no repair for a corrupt log line, memory-only approvals. Fine for a trial; not for data people rely on.
3. **Slot pinning and shared resources** (R-10): one patient attacker can fill the workspace cap, and all tenants share one process.
4. **Nothing has met real conditions**: a real proxy, TLS, a real browser against the new cookie flow (the frontend has not been changed to handle a missing workspace), real mail, a real model, real load. The first hosted trial is the first test of all of it.
5. **Single point of failure**: one process, one disk, restart from backup.

## What would make it ready for more
In order: build the durability phase (approvals, upgraders, verify/repair, hash chain); change the front end for the cookie, 404 and 403 states and test it in a browser against shared mode; choose and build a recovery route; run it behind the proxy you intend to use and load-test planning and asking; add alerting on `/readyz`, 5xx rate and disk; decide on expiry for idle workspaces that hold data; schedule backups and ship the deletion log; move to a database if you need more than one process.
