Records have no owner, so removal on request has nothing to match; the retention rule (90 days after expiry) and the off switch are the controls. | REVIEW: dormant, or wired to an owner-operated mailbox (the feature is kept; `docs/OWNER_DECISIONS.md` section B). |
| D-010 | A reply whose first line is only "stop" (with please or thanks) is a stop request, whatever signature follows; the anywhere-in-body patterns are not widened. | The footer asks for "Reply STOP", so the shapes people really send must work (R-015); a sentence that merely contains the word must not suppress a vendor. | |
| D-011 | The per-plan cap is per brief or plan id, so it restarts when a brief becomes a plan; the global 30/day is the real bound. | Keeping one counter across the two ids needs a link the store does not hold. | REVIEW |
| D-012 | The footer promises STOP handling on every first request, including ones the user copies and sends from their own mailbox ("Send it yourself"), where the app never sees the reply. | One fixed text keeps the approved hash simple. | REVIEW: consider a different footer for manual drafts ("if you would rather not hear from me, just say so"). |
| D-013 | A recorded quote prices an event only if it was given for that date, and a per-plate one only for a guest count it quoted or inside the vendor's own min/max. A quote with no date (a document line confirmed without a plan) never prices. A total-priced document quote carries no guest count, so for a caterer it is the user's statement for the plan they confirmed it on. | Audit A1: a quote for 300 guests on one date set the price of every other event. | REVIEW: the per-plate range rule trusts the vendor's stated range to hold the price. "Inside min/max" is the vendor's catalogue range, so a per-plate quote for 300 guests also prices 200 inside a 100 to 500 range. |
| D-014 | A reply held for the user keeps its words only: an attachment on a held reply is not read. After the user assigns it, the reply is stored like any other. A brief that became a plan files everything under the brief's id and the plan's id is an alias for it. | Reading a file for an event nobody has chosen would defeat the point; aliasing needed no move of existing records. | REVIEW |
| D-015 | Replies are found by asking the mail server for the threads we know (FROM the vendors, In-Reply-To / References our message ids, delivery notices), up to 200 a poll, newest first; the rest are counted and shown, not dropped. A few of the newest other messages are still read for stop requests and notices. A server that cannot search that way is read by window and the user is told. The spam folder is read only if `EVENTMATE_IMAP_SPAM_FOLDER` names it, read-only, into the user's review only. | Audit A3: "the last 50 since the oldest thread" lost older replies silently. | REVIEW: 200 and 20 are guesses; reading a spam folder is off by default. |
| D-016 | A request's status says what is known: written, queued, "accepted by the mail server (not proof it was delivered)", bounced, replied, or "you sent it yourself". The stored status is unchanged; the words are derived (`outreach_with_delivery`). | Audit A5. | |
| D-017 | OAuth (XOAUTH2) is added beside the app-password route, chosen by `EVENTMATE_MAIL_AUTH`; the password route stays the default. The refresh token is obtained once by the owner outside the app (their own client, e.g. the OAuth Playground) and is read from the environment only. The app builds no sign-in page and stores no token. | Google calls app passwords unnecessary and discouraged; a flow inside the app would put secrets in a browser and a store the project does not have. | REVIEW: a "Testing" consent screen gives tokens that last 7 days; the owner must decide whether to publish the app (unverified, single user) and confirm it in the real test. |
| D-018 | A request is called quiet after 3 days with no reply, in words only; nothing chases a vendor for the user. A menu priced in tiers is never resolved for the user, and a quote file's lines are evidence, never read into the price. Voice-note replies are not built. | The app's outbound rules (approval of exact text, caps, STOP) stay the only road out; a chase would be a new send. | REVIEW: 3 days is a guess. |
| D-019 | The payment route is not chosen. The app records terms, approves a payment against a hash of its exact content (amount, currency, payee, quote), and by default only tells the user what to pay; a PayPal sandbox adapter exists behind a flag that is off, with no live mode in the code. Hosted visitors can never use a provider. A payment is recorded paid only when a named person says so. No account or card number is stored. | The live prompt says not to pick Payouts as the default and to decide nothing about the route before the owner answers (BLOCKED.md). | REVIEW |
| D-021 | A payment whose outcome is not known (a lost answer, a 5xx or 429, a process that died while carrying it out) is never retried and never called failed: it stays live until the user says it went through or did not. | A retry could pay twice (R-020); calling it failed frees the slot for a second payment. | |
| D-020 | Outside services are watched, not retried or throttled by the app: each call records ok or a kind of failure (quota, unreachable, not configured, error), never the provider's words, and the page says when a lookup is used up or failing. The behavioural evals are capped in model calls and a capped run is never a pass. | A short list from a service that is used up looks like "no vendors exist"; evals must not spend more than a free allowance. | |
| D-022 | No host is chosen. The plan lists what free hosts say and what fits, as a reading, not a decision. | The owner's rule (recurring free only, no new account by us) and the unanswered questions in BLOCKED.md. | REVIEW |
| D-023 | **`requirements.lock` pins PyPI `flights==0.9.0`, but the pyproject `flights` extra names a git commit of fli (0.10.0)**, and the pyproject comment says 0.9.0 gets no fares. The CI test job (and `make ci-tools`) now installs the documented commit on top of the lock with `--no-deps` (`tools/ci/install_flights.sh`), and `tools/ci/require_tools.sh` fails if the installed flights is not that commit, so `tests/test_travel.py` runs on the fli the project documents (39 passed, 1 opt-in skip, checked). The lock comparison leaves the one `flights` line out and says so. | The two sources disagreed; tests had been running on the one the docs call unusable. | REVIEW: regenerate `requirements.lock` so it matches, or keep the override. |
| D-024 | CI is replaced by one gate (`make ci`, `tools/ci/`) that the workflows call; it is stricter than the old one on purpose: skips must be on an allow-list, mutants must be killed, the `/plan` build must reproduce, the tree must stay clean, the image is checked read-only with a leak control, and actions are pinned by sha. Nothing was run on GitHub. A first real run may need fixes for runner differences (docs/CI.md). | The reviewer's gate caught findings the old CI would have passed (G1 to G8). | REVIEW: branch protection, the `production` environment and `DEPLOY_ENABLED` are the owner's to set. |
| D-025 | **F8 (percent read as rupees), F3 (minus dropped).** `eventmate/moneytext.py` is asked by every parser that reads money (quote lines and typed confirms, the budget in a brief and in a change, quote documents, watches, page prices): a percentage is never a rupee amount (it is "unclear", the vendor's words kept, note "a percentage: type the amount in rupees"), and a minus sign or "minus" refuses the amount ("a budget cannot be negative"). A hyphen between words or numbers ("Budget - 2 lakh", "2-3 lakh") is not a sign. The terms and compare screens show the deposit as a share of the total (Rs 25 on Rs 54,000 reads 0.05%). No floor is invented, and the optional "25% of the confirmed total = Rs 13,500" button was not built. | A deposit of Rs 25 on a Rs 54,000 quote reached an approved payment; "budget -5 lakh" planned on Rs 5,00,000. | REVIEW: the percentage button is a decision for the owner. |
| D-026 | **F6 (privacy, SQLite-version dependent).** `PRAGMA secure_delete=ON` on every connection to a store of personal data (`eventmate/sqlsafe.py`), and a WAL checkpoint (TRUNCATE) or a vacuum after the registry deletes a workspace or a watch is removed. A test fails on any connection made without it. | The deleted workspace id stayed in a free page on SQLite 3.53.1 and not on 3.54.0. | none |
| D-027 | **F9 (a run quicker than the poll showed only its end).** Root cause on 3.12: the whole run took 0.09 s and the stream sampled every 0.1 s. The pulse now records every state of a run and the stream sends them all. Python 3.12 stays supported. | One picture reached the page. | none |
| D-028 | **F10 (the sandbox skipped on a uv interpreter).** `venv/bin/python` pointed at `cpython-3.12-linux-x86_64-gnu/bin/python3.12`, an alias directory of `cpython-3.12.13-...`; the sandbox mounted only the real directory, so exec found nothing. It now mounts the real files at every prefix the symlink chain names. Nothing else of the host becomes visible (a test lists the host paths). Proved on a uv 3.12 venv under /tmp: the four sandbox tests run and pass. | The first CI run would have failed the skip guard on a setup-python interpreter. | none |
