# Decisions

|---|---|---|---|
| D-001 | `docs/*.md` stay tracked (they already were); new docs are added with `git add -f` because `docs/` is in `.gitignore`. | The launch method needs HANDOFF, DECISIONS, BLOCKED and LAUNCH_PLAN reviewable on a sha. | REVIEW: the ignore line says docs are "not published for now"; tracked docs are public if the repo is ever pushed. |
| D-002 | The borrowed artwork was never committed; it was moved out of the tree to `../_quarantine-borrowed-art/` (with its source notes) and replaced by SVG drawn for the project. | Pixel crops of outside images and a third-party character, rights unverified. Never in history, so no rewrite is needed. | REVIEW: the new look (a hand-drawn ink style, a party-hat mascot) is a design change the owner should see. |
| D-003 | `papers to refer/` (PDFs of papers) and `*.egg-info/` are git-ignored. | Third-party publications are not ours to republish; egg-info is a build product. | |
| D-004 | B108 at `documents/isolation.py` is suppressed with `# nosec B108` and a reason. | The path is a tmpfs inside the bubblewrap sandbox, not a host temp file. | REVIEW |
| D-005 | The approvals race test now builds its child queues with the same fixed clock as the proposal. | It used the real clock, so once the date passed the 7-day expiry the proposal read "expired". | |
| D-006 | The landing hero poster/video were removed, not kept as optional. | Licence unconfirmed; an optional, absent file added code paths (tag stripping, 404 handling) for nothing. The hero is a plain gradient. | REVIEW: restore a hero only with a confirmed licence. |
| D-007 | Per-plan cap is 10 first requests/day (follow-ups not counted); the cap holds the 11th with a reason instead of refusing it. | One brief should not spend the whole 30/day. Held requests stay approved and go the next day. | REVIEW: the number 10 is a guess. |
| D-008 | The sender line and STOP instruction are fixed text appended to every first request, not editable. | Vendors must always be told who wrote it and how to stop; being in the body, the approval hash covers it. | |
| D-009 | The shared quote pool stays dormant; pasted replies are never added; it stores the month of the event, not the day; no per-person deletion. | Anyone could type any price, so a pasted reply cannot feed it. With the exact date, anyone who knew a person's vendor could read when their event is. Records have no owner, so removal on request has nothing to match; the retention rule (90 days after expiry) and the off switch are the controls. | REVIEW: dormant vs wired to an owner-operated mailbox vs removed (BLOCKED.md). |
| D-010 | A reply whose first line is only "stop" (with please or thanks) is a stop request, whatever signature follows; the anywhere-in-body patterns are not widened. | The footer asks for "Reply STOP", so the shapes people really send must work (R-015); a sentence that merely contains the word must not suppress a vendor. | |
| D-011 | The per-plan cap is per brief or plan id, so it restarts when a brief becomes a plan; the global 30/day is the real bound. | Keeping one counter across the two ids needs a link the store does not hold. | REVIEW |
| D-012 | The footer promises STOP handling on every first request, including ones the user copies and sends from their own mailbox ("Send it yourself"), where the app never sees the reply. | One fixed text keeps the approved hash simple. | REVIEW: consider a different footer for manual drafts ("if you would rather not hear from me, just say so"). |
| D-013 | A recorded quote prices an event only if it was given for that date, and a per-plate one only for a guest count it quoted or inside the vendor's own min/max. A quote with no date (a document line confirmed without a plan) never prices. A total-priced document quote carries no guest count, so for a caterer it is the user's statement for the plan they confirmed it on. | Audit A1: a quote for 300 guests on one date set the price of every other event. | REVIEW: the per-plate range rule trusts the vendor's stated range to hold the price. |
| D-014 | A reply held for the user keeps its words only: an attachment on a held reply is not read. After the user assigns it, the reply is stored like any other. A brief that became a plan files everything under the brief's id and the plan's id is an alias for it. | Reading a file for an event nobody has chosen would defeat the point; aliasing needed no move of existing records. | REVIEW |
