# Integrations: what each service says, where, and when it was read

Every row is from the service's own page. "Read" is the date a current copy of the page was fetched and read for this project. Services change these pages; read them again before relying on a row. A row marked **unverified** was not read from an official source and must not be built on. Nothing here is a statement that a live round trip happened: see `docs/BLOCKED.md` for what has not been run.

## Gmail mailbox (WP2: the dedicated mailbox)

| Fact | Source | Read |
|---|---|---|
| IMAP, POP and SMTP all support OAuth 2.0. IMAP `imap.gmail.com:993` (implicit TLS); SMTP `smtp.gmail.com:465` (implicit TLS) or `:587` (STARTTLS) | https://developers.google.com/workspace/gmail/imap/imap-smtp (page dated 2026-11-03) | 2026-11-09 |
| SASL XOAUTH2: the initial client response is base64 of `user=<user>\x01auth=Bearer <access token>\x01\x01`; the scope is `https://mail.google.com/`; an error comes back as a base64 JSON challenge (`status`, `schemes`, `scope`) and the client sends an empty line; IMAP `AUTHENTICATE XOAUTH2`, SMTP `AUTH XOAUTH2` | https://developers.google.com/workspace/gmail/imap/xoauth2-protocol (page dated 2026-09-15) | 2026-11-09 |
| An IMAP session lasts about 24 hours, and with OAuth about the life of the access token (usually 1 hour): reconnect and authenticate again | the IMAP/SMTP page above | 2026-11-09 |
| Sending: up to 500 messages a day from a personal Gmail or Workspace trial account and 2,000 from a paid Workspace account, up to 100 recipients per message over SMTP, per user and shared by every client; "more than 500 emails sent in a day" gives a block that lifts in 1 to 24 hours; many bounces or invalid recipients can also block sending for about a day | https://support.google.com/mail/answer/22839 and the IMAP/SMTP page | 2026-11-09 |
| App passwords: "aren't recommended and are unnecessary in most cases"; they work only with 2-Step Verification on; they are not offered for accounts with 2-Step Verification set up only for security keys, for work or school accounts, or with Advanced Protection; changing the Google password revokes them; each is shown once | https://support.google.com/accounts/answer/185833 | 2026-11-09 |
| Refresh tokens stop working when: the user revoked access; **the token has not been used for six months**; the user changed the password and the token has Gmail scopes; the account passed its limit of live tokens (100 per account per client; the oldest is replaced without warning); time-limited access ended; an admin restricted the service. **A project whose consent screen is "External" with publishing status "Testing" is issued refresh tokens that expire in 7 days** (unless only name, email and profile scopes are requested) | https://developers.google.com/identity/protocols/oauth2 (page dated 2026-10-29), section "Refresh token expiration" | 2026-11-09 |
| The token endpoint is `https://oauth2.googleapis.com/token`; a refresh token is returned only on the first authorization with `access_type=offline`; the refresh exchange is the standard `refresh_token` grant (RFC 6749 section 6) | https://developers.google.com/identity/protocols/oauth2/web-server (page dated 2026-10-30) shows the endpoint and the code exchange; the refresh request itself was **not re-read on that page**: confirm its fields in the real round trip | 2026-11-09 |
| The consent screen: choose a user type (internal or external), add scopes, and for an external app add test users; sensitive and restricted scopes need verification for public apps | https://developers.google.com/workspace/guides/configure-oauth-consent (page dated 2026-09-03) | 2026-11-09 |
| The OAuth 2.0 Playground can run the flow with your own client credentials | linked from the OAuth page above; the Playground itself was not opened | 2026-11-09 |

What this project does with it: `eventmate/messaging/mail_oauth.py` (token source and the XOAUTH2 string), `EmailChannel.login_smtp` / `login_imap` (`eventmate/messaging/channels.py`), `EVENTMATE_MAIL_AUTH=password|oauth2`. The password route is unchanged and the default.

**What is verified and what is not.** The XOAUTH2 string equals Google's documented example byte for byte, and Python's own `smtplib.auth` and `imaplib.authenticate` complete the exchange, including the error challenge, against small local servers that speak the documented dialogue (`tests/test_mail_oauth.py`). **Not verified:** Google's real servers accepting this client; the real token endpoint's answer to the refresh request; whether a refresh token for the owner's account lasts (the "Testing" 7-day rule above); IMAP `SEARCH` quoting and `HEADER` search against a real Gmail mailbox (the fake server answers what the app asks, which proves the app asks it, not that Gmail answers it the same way). All of this is "not run" in `docs/BLOCKED.md`.

## Payments (WP4): what each route says, and what is NOT known

Nothing here was run. The route is **not chosen**: the owner's answers are needed first (which country the PayPal account is in, whether it is a business account, whether the vendors have PayPal, whether they are in India). The app has a manual instruction (moves nothing) and a PayPal **sandbox** adapter that is off by default.

| Fact | Source | Read | Verified? |
|---|---|---|---|
| PayPal Payouts sends money out of a **PayPal business account's own balance**: it needs a business account, access to Payouts (applied for; PayPal emails the decision, and the sandbox can be used meanwhile), a confirmed identity, email and linked bank account, and enough funds | https://developer.paypal.com/docs/payouts/standard/ | 2026-11-09 | read from the page |
| The country table lists **India as "Receive and withdraw"**, not "Send": an account registered in India cannot send payouts. Currency conversion is not available for payouts to India (or China, South Korea, Taiwan, Thailand, Turkey). Page dated 2026-09-10 | https://developer.paypal.com/payouts/supported-features | 2026-11-09 | read from the page |
| Orders v2 (a merchant's checkout: payer pays the merchant) and Invoicing v2 (a merchant invoices a payer) are for a merchant **collecting** money; they fit only if the vendor is the merchant or the owner collects | https://developer.paypal.com/docs/api/orders/v2/ , https://developer.paypal.com/docs/api/invoicing/v2/ | 2026-11-09 | endpoint lists read; whether either fits this project is **unassessed** |
| Sandbox base `https://api-m.sandbox.paypal.com`; token: `POST /v1/oauth2/token` with HTTP Basic `client_id:secret` and `grant_type=client_credentials`, then `Authorization: Bearer <token>`; sandbox accounts behave like live ones with mock money | https://developer.paypal.com/api/rest/authentication/ , https://developer.paypal.com/tools/sandbox/ | 2026-11-09 | read from the pages |
| Payouts API: `POST /v1/payments/payouts` (create batch) and `GET /v1/payments/payouts/{id}` (batch status) | https://developer.paypal.com/docs/api/payments.payouts-batch/v1/ | 2026-11-09 | endpoints read; the **request body fields** (`sender_batch_header`, `items[].recipient_type/receiver/amount/note/sender_item_id`) and the `PayPal-Request-Id` idempotency header are **not re-read from the spec page** and come from the public Payouts reference: the sandbox run is what verifies them |
| "PayPal India: you can't receive domestic payments (international supported)" | https://www.paypal.com/in/cshelp/article/can-i-use-paypal-to-receive-payments-from-indian-customers-help1049 | **could not be read** (HTTP 403 to a plain request) | **unverified**: relies on the owner's note |
| UPI: a payment link or QR from the vendor's UPI id that the user pays in their own UPI app | NPCI's UPI linking specification, https://www.npci.org.in/ pages | **could not be read** (HTTP 403) | **UNVERIFIED. Nothing is built for it.** The manual instruction shows the vendor's UPI id and the amount for the user to pay in their own app |
| Razorpay Payment Links: "create and send links to collect money" (a merchant collecting), methods include UPI, cards, netbanking; Payment Links page last modified 2026-10-08 | https://razorpay.com/docs/payments/payment-links/ | 2026-11-09 | read; fits an owner collecting from customers, **not** an app paying vendors; KYC needed for a live account (the KYC page exists; its terms were not read) |
| Razorpay pricing: "2%" per successful payment, no setup fee or annual maintenance charge, shown on the pricing page | https://razorpay.com/pricing/ | 2026-11-09 | read; **a quote of the page's headline, not a statement of what this project would pay** |
